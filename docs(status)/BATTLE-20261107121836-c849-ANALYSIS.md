## 7. 副指挥官附注：残余风险与未验证项（人工补充，非机械统计）

「缺口与风险 (0)」指机械审计口径（批次/证据/不变量覆盖），**不等于**没有残余风险。以下为本次
战役结束后仍成立、且已同步进 `docs/status.md` 的限定：

1. **NeoForge 端到端未验证**。本轮真机证据只有 Forge 1.21.1（ForgeGradle 7 `runServer --offline`）。
   NeoForge 与 Forge 共用 `ModLauncherMixinBridge` / `ForgeMixinHotSwap` / `ForgeClassInfoSync`，
   但没有任何 NeoForge `runServer` 证据：Mixin 加载层、`MixinEnvironment` 选择时机、EventBus
   刷新路径都可能不同。不要拿 Forge 证据覆盖 NeoForge。
2. **生产 jar 声明路径未验证**。探针运行在 dev 运行时（FG7 无 jar manifest），Mixin 配置由
   `MixinEnvironment.addConfiguration` 手动注册；生产模组走 `mods.toml` + manifest `MixinConfigs`
   的路径未在探针中覆盖。真实模组/客户端、生产 refmap 同样未验证。
3. **E2E 归因的语义边界**。驱动（`run-forge-classinfo.sh`）只报告「reload 是否被接受」
   （`success` / `rejected` / `not-attempted`）；「成员是否真的到达目标类」由探针的业务断言
   （`CI-M1` handler 每次调用 +1、`CI-M2` 新增 `@Unique` 读到初值 456、`CI-PRESERVE-*` 既有成员
   保持）承担。两者合起来才构成「修复生效」的证据，任何一半单独出现都不足：例如只看到
   `reload=success` 而 `CI-M1` 为 FAIL，Verdict 判 RED。
4. **探针自身的两次无效运行**保留在 `evidence/invalid/`：一次是 harness 用了目录里最旧的
   `plugin-forge-0.2.0.jar`（修复前的包，reload 从未发生），一次是 stage 归因窗口过窄（worker
   线程的 re-woven 日志落在下一 stage 窗口）。两次都不是产品缺陷，相关修复已在 batch A 提交，
   记录保留以免「静默丢弃不利证据」。
5. **变异检查的斩杀方式**：反向应用实现 diff 后用例变红属于「编译/反射类名缺失 + 断言失败」，
   不是单一断言的精确击杀；`ForgeClassInfoSync` 的单元测试同时覆盖了「去掉 reload 前同步」
   （`sawNewMemberBeforeReload` 为 false）这一更贴近单一改动的击杀面。
