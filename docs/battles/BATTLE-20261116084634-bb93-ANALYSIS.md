### 2.1 台账口径说明（为什么会出现 `exit 1 · PASS` 与 4/5、5/6）

- **`exit 1 · PASS` 的语义**：`battle_probe` 的 PASS 判据是"**退出码符合 `expect_exit`**"，不是"测试全绿"。
  `ev-20261116085328-9bb9` 是刻意用 `expect_exit=1` 取的 TDD 红基线（跨类映射用例必须失败），
  所以它在台账里是 PASS（红基线已被证实）。
- **表格分母的口径不同**：§2 的"探针(通过/总)"按 **exit==0** 统计，于是同一行在台账显示 PASS、在表格里
  却算"未通过"——L 的 4/5 就是红基线那 1 条；U 的 5/6 是修复前的编译失败。
  两者不是"当前代码还有红探针"。
- **`ev-20261116085136-1efd`（exit 1 · FAIL）**：批次 U 修复前的 TDD 编译失败（夹具误用不存在的
  `NoSuchMethodError(Throwable)` 构造器），同批次内已修复，之后的 `ev-20261116085229-c727` /
  `ev-20261116085453-81de` 为同批次的通过记录。台账没有 "superseded / BASELINE-FAIL" 状态
  （`battle_invalidate` 的语义是"证据不可信"，不适用于一条真实的红基线），因此它只能以 FAIL 留在台账里，
  **不代表终态失败**。
- **已作废 3 条**：`f764`、`c5f9`（Windows cmd 跑不了 `./gradlew`，harness-error）、`43d9`
  （`> Task :tests:test UP-TO-DATE`，缓存命中未真跑）。
- **残余风险**：审计只要求每批有通过探针 + 变异击杀，没有"同一 label 的最新探针必须绿"的终态对账规则；
  本轮靠人工在战报里逐条点名，未形成机械阻断。

### 5.1 已接受局限 / 挂账债务（非零）

1. **`CellPropertyRef` 程序分析与执行手段的深度边界**（`docs/status.md` 风险 22）：
   - 静态链提取用原生 `SourceInterpreter`，只接受单来源（`insns.size()==1`），三元/栈复制即放弃静态参数；
   - 提取阶段无宿主方法控制流判据（`if`/循环内同签名站点顺序），依赖运行期 `slotCursor` 回填；
   - `verifyBytecode` 用一次性 `ClassLoader.defineClass`、`applyChainUpdate` 每轮 `new Table()` dry-run、
     `LambdaInfo` 走 `Proxy` + `MethodHandle`。三项属"运行期试跑"路线，未做基准，未重写。
   - 重开条件：出现可复现的 UI 属性错配现场（含最小字节码形态）。
2. **真机 DCEVM 批次未端到端复跑**：跨类映射的红→绿只到"真实编译产物 + 单元消费者"层级，
   未在 Mindustry/JBR 宿主里跑一次含多 UI 类的真实批次。按项目纪律（AGENTS §8.6），本战役结论只能表述为
   "已定位 + 加防护 + 单元回归锁定"，**不是**"真机已验证"。
3. **合流时序风险**：L/U 直接合入 `main`（17:04），联合全量门禁 `ev-20261116091313-5fb2` 在 17:13 才完成。
   期间 `main` 的联合验证只有"U 合流后跑 U 验收（该树已含 L，联合编译被覆盖）"，**L 的用例未在联合树上重跑**，
   union 全量要等到 17:13。L/U 写域不相交（L：`LambdaAligner` + `CellPropertyRef`；U：`UpdateRef`），
   语义冲突概率低，但这不是免除联合验证的理由。建议合流在临时 integration worktree 里完成 Merge + union 全量，
   绿灯后再 FF 合入基线。
4. **main 在封版后继续漂移**：封版提交 `1509c42` 之后，另有会话向 `main` 推进了
   `4ef756a`（18:25，build-trigger marker）与 `9e086f5`（18:29，merge）。因此 `ev-5fb2` 的全量证据对应的是
   `dc2cbd1`，**不能代表当前 `main`**；本战役的验收范围止于 `dc2cbd1`。
