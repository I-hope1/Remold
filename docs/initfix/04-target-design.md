# 04 目标设计（设计规格；路线图与状态见 status.md）

本文件只描述设计与目标架构，**不登记实现状态、路线图状态或验收证据**；这些统一以
[`docs/status.md`](../status.md) 为准（路线图见其 §4.1/§4.2，读穿窗口的通道级状态见其风险 9）。
不要把这里尚未落地的条目当成已有功能调用。

## 1. 两阶段 Schema-First 重定义

**目的**：消除新方法体在热更瞬时读到未就绪字段的 NPE（读穿），以及 `static final` 的 JIT 常量折叠。

**适用条件**：只对**schema 变更**（本批存在真正会写的零值暴露字段：新增/类型变更字段进入补丁计划）
编排两阶段；纯方法体热更不触发本机制，不必付第二次 redefine 的代价。**通道级接入状态与仍敞开的读穿
窗口**（单阶段开关、外部 IDE/JDWP）见 `docs/status.md` 风险 9——本节不承诺"所有通道都已关闭"。

**编排位置**：三个阶段的编排既可以在批次内完成，也可以完全发生在**一次公开 API 调用内部**
（单类动态入口：A → 补丁 → C 同步跑完，返回时已是阶段 C）。两种位置都不向调用方暴露阶段 A
中间态，阶段 C 一律复用分析期已生成的终态字节，不重跑字节码桥接或补丁装配。

**时序**
1. **阶段 A（骨架先行）**：提交 Stage A 字节码：新结构就位，**除 `<init>`/`<clinit>` 外的既有方法**继续跑旧执行体（旧逻辑在编译期不认识新字段，绝不读它们）；构造器/静态初始化器保留新体，阶段 A 之后新建的实例由新构造器直接完成初始化。
2. **阶段 B（补丁）**：伴生类对存量实例执行条件 CAS。字段级失败按既有台账语义记账；阶段 A 已经生效，JVM 无法回退，因此「中止 = 不提交阶段 C、停在阶段 A」。
3. **阶段 C（全量上线）**：提交完整新字节码，新方法体开始执行。

**阶段 A 成员构成**
- 预注入所有全新增加的私有方法、新 Lambda（`forceStaticLambdas` 保持签名稳定）、内部类，以及 T4 目标
  设计中的 `@HotswapInit` 静态方法（见下文「T4 调用」）。
- 旧代码无调用点，新成员休眠，保证阶段 B 伴生类链接合法。
- **构造器与 `<clinit>` 保留新执行体**（`StageASkeleton.buildWithLiveConstructors`）：阶段 B 的堆快照到阶段 C 之间不再有第二次枚举，窗口内新建的实例只能靠新构造器拿到真实初值。
- **字段同样按旧 ∪ 新并集处理**（按 `name + desc`）：被删除的旧字段、类型变更前的旧描述符字段都会在阶段 A 保留，旧方法体才能继续链接；阶段 C 才收敛到严格的新字段表。

**骨架合成契约（`StageASkeleton`）**
- 以**新类**为骨架，把旧方法的执行体搬回：新字段、新方法、新内部类就位；**回退范围 = 除构造器/`<clinit>` 外的全部既有方法**。
- 构造器为什么不回退：旧构造器不会初始化新增字段，而阶段 A→C 之间新建的实例不会再被补丁覆盖（补丁只枚举快照时刻的实例）。让构造器跑新体，等价于 `ConstructorTailInjector` 的插桩目标，但不需要从切片反推「取值指令」；旧非构造器方法体在编译期不引用新增字段，因此窗口内不会读穿。
- 这条契约与初版设计的差异是**放弃「阶段 A 行为完全惰性」**：若阶段 B 失败并停在阶段 A，新实例已经按新构造器初始化，而方法体仍是旧行为，属于「不一致但可用」的失败态（需要重启）。换取的是不需要切片提取/插桩、窗口实例天然完整。
- 成员按**旧 ∪ 新**处理：新版本删掉、但旧执行体仍在调用的方法必须留着休眠，否则阶段 A 一执行就 `NoSuchMethodError`；阶段 C 才提交严格的新结构。
- 搬运不移交拷贝：旧 `ClassNode` 用完即弃，旧 body 的 label、栈帧、局部变量表整体挂到新方法节点上，栈帧天然有效；写入侧仅 `COMPUTE_MAXS`。
- 静态性/抽象性/native 性变化的方法不搬运旧体（旧体对新签名非法），这类变化由上游安全门拒绝。

**切片调用防护（核心原则）**
- 切片（含递归调用闭包）禁止调用"已存在但本次被修改"的方法，否则阶段 B 会执行旧方法体算出过期值。
- 此时必须拒绝打补丁，或由 Emitter 把新方法体克隆进伴生类。

**T4 调用（目标设计）**：阶段 A 预注入 `@HotswapInit` 静态方法，伴生类通过静态调用转发，从而无需
克隆方法体；契约见 [`09-hotswapinit-design.md`](09-hotswapinit-design.md)。该能力的落地状态见
`docs/status.md` §4.1，本文件不重复。

**`isInitialized` 二次检查**：阶段 A 提交成功后、阶段 B 执行前再检查一次。若类处于 `being_initialized`，说明其他线程正在执行旧 `<clinit>`，立即中止本次热更。

**字节码来源（两个阶段用不同的字节码）**
- **分析**（切片提取、补丁装配）必须用**阶段 C** 字节码：阶段 A 的**非构造器方法**是旧体，里面没有新字段的初始化式，拿阶段 A 去抽切片只会得到「没有安全的初始化表达式」。阶段 A 的构造器虽然保留新体，但补丁分析仍应以 C 为准（阶段 A 可能因为中止/边界原因与 C 不一致）。
- **提交**分别用阶段 A 与阶段 C 字节码；`bytecodeCache` 在分析期必须指向阶段 C，否则层级 Oracle 从加载器读到旧版本、找不到新字段，字段访问会被判成「无法确定 protected 状态」而整批拒绝。阶段 A 提交后，缓存改为指向阶段 A（JVM 当前真实形态），阶段 C 成功后再推进到 C。

**中止后的基线**：阶段 A 已生效、阶段 C 未提交时，基线哈希推进到阶段 A 的骨架字节码，未补字段进
`FieldLedger`（见 `02-closure-and-ledger.md` §2）；下一轮 diff 的旧字节以 `bytecodeCache` 里的阶段 A
为准。契约是"停在阶段 A + 提示重启"，不做自动回滚。

**阶段 C 的第二重作用（JIT deopt 屏障）**：补丁写的是内存（实例字段、静态字段），不会通知 JIT
退优化；在阶段 A 到阶段 B 之间抢跑重编译、把补丁前的零值/旧值提升进机器码的读者，由阶段 C 的第二次
redefine 统一退优化，后续重编译读到补丁值。该屏障对运行时初始化的 `static final` 引用字段的读者同样
成立（实测见 `docs/topology/10-enum-constant-append-infeasibility.md` §3.4.2）；`ConstantValue` 编译期
常量除外（读者已内联字面量，deopt 无法改回）。

## 2. `PatchPlan` 基线指纹

- `baseClassHash` 指向经 `AnnotationTransformer`（`forceStaticLambdas` 等）规范化、传给 JVM redefine 的字节码哈希，不是磁盘原始字节码。
- Target 端记录当前类实际字节码哈希，执行前比对，不匹配则拒绝执行并触发重新分析。
- `PatchPlan` 需可序列化，并携带前置指纹与版本向量。

## 3. Analyzer 库化

- 目标：Analyzer 是无外部状态依赖的纯函数，既可嵌入 JVM Agent（IDE 单机快速热更），也可在构建端（Gradle/PC）执行。
- 流水线：旧/新 Class 字节码 + `ClassHierarchyOracle` → Analyzer → 策略配置 → Planner → Emitter → 可序列化 `PatchPlan`。
- 执行隔离边界之后是 Target/Runtime Driver：基线校验、两阶段驱动、堆实例收集、伴生类加载与逐字段执行。

## 4. 构造器尾部插桩

**要解决的缝隙**：从阶段 B 堆遍历快照到阶段 C 提交，受全堆 STW 影响耗时可达毫秒到秒级，期间新建的对象可能漏补。

**方案**：在阶段 A 的所有构造器尾部（`RETURN` 前）注入新增字段的切片代码。阶段 A 之后新建的对象在构造器里直接带真实参数完成初始化，缝隙在物理上封死，无需增量全堆扫描。

**插桩器契约（`ConstructorTailInjector`）**
- 纯函数：输入阶段 A 字节码 + 每字段的取值切片（从空栈开始、执行后栈顶为该字段的值），输出改写后的字节码；不读写全局状态、不触发类加载。
- 只改写**根构造器**：以 `this(...)` 开头的构造器整条跳过，避免同一切片沿委托链重复执行。
- 构造器体内**已自行赋值**目标字段时整条跳过并报告原因——构造器自身逻辑优先，插桩绝不覆盖。
- 在**每个** `RETURN` 前插入，多返回路径全覆盖；没有 `RETURN` 的构造器（恒抛异常）跳过，该路径不会让对象逸出。
- 栈帧：只插入直线代码、不改任何跳转目标，原有 `FrameNode` 继续成立（`RETURN` 前与本类插入的 `ALOAD 0` 前都是空栈、同样的局部变量表）；写入侧仅 `COMPUTE_MAXS`，不重算栈帧——与匿名类对齐器同源的防类加载死锁约束。

**两阶段契约下的接线边界（设计）**
- 阶段 A 保留新构造器/`<clinit>`（见 §1），窗口实例由新构造器初始化，因此**不需要**构造器尾部插桩；
  `ConstructorTailInjector` 只在"要求阶段 A 的构造器也回退旧体"这一备选契约下才需要。接线状态见
  `docs/status.md` §4.1。
- 补丁只重放字段初始化式，构造器里的其它语句不会为存量实例重放。
- 新增字段在构造器里被使用（如 `sb.get().append("aass")`）：默认拒绝，存量实例保持默认值（漏补而非误补）。
- 用 `@RemoldReinit` 豁免后放行，但会 warn 并写入 `FieldDecision.warnings`。

**已知边界**：堆遍历抓到其他线程正在运行 `<init>` 且尚未赋值 final 源字段的对象，可能算出非预期初值。此类依赖参数回溯的字段应在报告中标为已知风险。

## 5. 跨类批次拓扑排序

若类 `X` 的新增字段表达式读取类 `Y` 的新增字段，两类须打包为同一事务批次：Stage A 全量生效 →
按拓扑序执行 Stage B → Stage C 全量生效。类内拓扑排序是既有契约（实现状态见 `docs/status.md`）；
跨类批次排序的设计见本节。
