# v0.2.6 Release Notes

Status: **released 2026-11-09** (`v0.2.6`, GitHub release published; tag `2159d21`).
Previous release: `v0.2.5` (`78673b2`).

## Highlights

- **Two-phase Schema-First redefine closes the read-through window.** `redefineClasses` returns before
  `InitFix` has written the newly added fields, so a reader in that window can observe `null` / `0` (a
  real `NullPointerException` on render/logic threads). On the internal batch path (file watch →
  `processChanges`) Remold now commits **stage A** — the new class structure with the **old** method
  bodies, while constructors and `<clinit>` keep the new bodies — then patches live instances, then
  commits **stage C** (the new bodies). The old bodies cannot reference fields that did not exist at
  compile time, so they cannot read through the window; instances created between A and C are
  initialized by the new constructors. Pure method-body edits keep the single-redefine fast path. On by
  default; `-Dremold.agent.two_phase=false` restores the previous behaviour.
- **Initializer replay for objects that already exist — both channels opt-in.** A double-brace
  initializer (`new Unit() {{ health = 250; }}`) that writes an inherited field, and a Kotlin `object` /
  top-level `val` holder whose `<clinit>` runs `Turret("duo").apply { health = 250 }`, now replay the new
  compile-time constant onto live objects. Both are gated by an explicit allowlist
  (`-Dremold.agent.init_drift.parents=...`, `-Dremold.agent.init_drift.apply_holders=...`; empty = off)
  and write through the new `HotswapBridge.KIND_CONDITIONAL_EXPECTED` protocol: a value is written only
  while the instance still holds the **old** constant, so a runtime-modified value (a damaged unit's
  health) is never overwritten. Neither channel writes `FieldLedger` or changes `patchGenerated`.
- **Mixin anonymous-class / inner-class hot-swap.** The first anonymous class introduced inside an
  `@Inject` handler used to kill the reload (`Error loading class: Outer$1 (ClassNotFoundException)`,
  then `innerClass is null`); editing only the body of an already-loaded generated inner class used to
  end in a silent `[DYNAMIC-REDEFINE] no-op` while the old body kept running. Remold now feeds the new
  bytes into Mixin's own bytecode provider (`MixinBytecodeOverlay`, with the upstream negative
  `ClassInfo` cache entries evicted) and redefines the generated `Target$Anonymous$<uuid>` class in place
  (`MixinInnerClassHotSwap`, `MixinInnerClassSupport`). Weaving-generated classes can also register
  their bytes in `core` `BytecodeSources`, so Nest scanning and InitFix's constructor-visibility check
  resolve them instead of failing closed; `refeedForTarget` pre-generates a freshly woven target's
  synthetic inner classes after weaving and before the InitFix scan, then restores `loadCounter` so the
  platform still performs the real `defineClass`.
- **Same-shape anonymous-class ambiguity and holder-field naming.** When two anonymous classes in one
  method share an interface and structure, topology alone can no longer decide and the edit used to be
  orphaned. A body-structure similarity tier (anonymous-class references masked, literals excluded,
  strict margin, both-way unique) now decides the R2b case; only if it fails does an approved liveness
  fallback pair a whole ambiguity group whose old candidates all have zero live instances. The orphan
  warning names the holder fields — proven by the assignment flow (`NEW <anon> → <init> → PUTFIELD`) or
  listed as candidates when the field is declared as the anonymous class's supertype/interface (the
  `Supplier`-typed holder case).
- **Start-up readiness gate and batch stall watchdog.** `api` gained `HotswapPlugin.isHostReady()`
  (default `true`); `StartupGate` holds batches until the host says it is ready, with
  `-Dremold.agent.ready_timeout_ms` (default `0` = never releases on time). `BatchWatchdog` dumps all
  thread stacks **once per batch** with `[HOTSWAP-STALL]` when a batch exceeds
  `-Dremold.agent.batch_stall_ms` (default `15000`, floor `5000`); the funnel now covers the debounce
  batch, the manual `triggerHotswap()` entry and `retransformLoaded`.
- **Structured batch report, client HotSwap toast, template back on 1.21.1.** `api` gained
  `HotswapBatchReport` and `HotswapBatchListener.afterInternalBatchReport()` — batch elapsed time, Mixin
  member deltas (with an explicit "delta unknown" state) and InitFix patch counts — populated by the new
  `core` `BatchReportScope`. The Fabric template's client toast consumes that report and shows an
  explicit "legacy agent" card on the published 0.2.5 agent instead of fabricating zeros. The template
  baseline moves back to Minecraft 1.21.1 (yarn 1.21.1+build.3, loader 0.16.9,
  fabric-api 0.105.0+1.21.1); the 1.21.4-only client gametest is preserved as the standalone
  `tests/fabric-gametest-1.21.4/` probe.
- **Class and asset debounce are separate streams.** Every `.class` / `.jar` event resets the **Class**
  quiet window (default lowered to **800 ms**); resource/config events use their own **250 ms** window
  and never postpone a Class batch. A pure `DebounceWindow` state machine (unit-tested without sleeping)
  decides which stream is due; the manual `triggerHotswap()` entry still cancels the pending timer,
  clears both deadlines and force-drains all queues. The Gradle DSL gained `assetShakeMs`.

## Fixes

- Read-through `NullPointerException`: a reader running between `redefineClasses` and `InitFix` observed
  `null` / `0` for a newly added field. Closed on the internal batch path by the two-phase redefine
  above; the external IDE/JDWP and `redefineDynamic` channels still run single-phase and are listed
  under Known limits.
- Mixin handler's first anonymous class: `ClassNotFoundException` for `Outer$1` followed by
  `Cannot invoke "ClassInfo.isProbablyStatic()" because "innerClass" is null` no longer happens — the new
  bytes are offered to Mixin's bytecode provider before `reloadMixin`, and the negative `ClassInfo`
  cache entries are evicted.
- Body-only edit of an already-loaded Mixin-generated inner class: used to end in
  `[DYNAMIC-REDEFINE] no-op` while the live class kept the old body; the generated
  `Target$Anonymous$<uuid>` class is now redefined in place. The "no-op" line that follows for the
  target class is expected and is now explicitly explained in the log.
- `NoClassDefFoundError: LoadedTargetSuppressor` disabled both the success and the failure branch of the
  Mixin hot-swap handler under a plugin/core version skew. The "target already loaded" suppressor now
  crosses the core boundary as plain JDK `Function` / `Consumer` method references, so the same skew
  degrades to a diagnosable "suppression unavailable" path instead of a linkage error.
- Same-shape anonymous-class edit: previously orphaned (`topology-equal candidates 2 -> 2,
  topology-decided 0`) with the field-held live instances still running the old body. It is now decided
  by body evidence, then by the liveness fallback; the warning names the old classes with their
  live-instance counts, the holder fields and the `@RemoldReinit` escape hatch.
- A field whose initializer allocates a Mixin-generated anonymous class was refused on hot reload
  (`Nest scan incomplete`; `Field init patch refused ... cannot determine protected status of
  constructor`). Synthetic bytes can now be registered in `BytecodeSources`, and the diagnostics name
  the weaving-generated synthetic class as the cause instead of failing unattributed.
- A Mixin name removed from `*.mixins.json` could be silently re-registered when its class file was
  rewritten; the removal now holds until the name is re-added, and a re-add whose asset event was missed
  is re-checked on the next class rewrite (the recorded config path is re-read). On Forge/NeoForge,
  `ModLauncherClassTrackerSpoof` removes target names from `ModLauncherClassTracker.loadedClasses`
  inside the `prepare()` window, restores them in `finally`, and fails closed when the tracker shape is
  unknown; `ForgeMixinConfigDiff` wires `onAssetsChanged` to the shared engine.
- The batch stall watchdog previously covered only the debounce Class batch (manual `triggerHotswap()`
  and `retransformLoaded` were uncovered). It now arms through a scoped `enter` / `exit` API with at
  most one armed watchdog per batch.
- Gradle plugin: the agent JVM arguments were injected only into the loader `client` run container, so
  `./gradlew runServer` (Fabric Loom / ForgeGradle / ModDevGradle) and Fabric gametest runs
  (`clientGameTest` / `gameTest`) started without `-javaagent`. Client, dedicated-server and gametest
  runs now receive the same arguments; auto-deploy also wires `runServer`, and the IDEA Loom sync covers
  `Minecraft_Server.xml` as well as `Minecraft_Client.xml`.
- Release tooling: the Gradle plugin's JitPack publication published the bare version while the packaged
  `remold.gradle(.kts)` shims and both project templates request
  `com.github.I-hope1.Remold:gradle-plugin:v<version>`, so offline / `mavenLocal` resolution of the
  plugin dangled. Publications now use the `v`-prefixed version, `panama` gained its missing JitPack
  publication, and all consumer coordinates are canonicalized to the real repository account casing
  (`com.github.I-hope1.Remold`), which also removes a Gradle module-metadata group-case mismatch.

## Added

- `api`: `HotswapBatchReport` (immutable, safe to pass across threads; `MixinChange` with an explicit
  `deltaKnown` state, `InitFixStats` that only counts completed patches),
  `HotswapBatchListener.afterInternalBatchReport()`, `HotswapPlugin.isHostReady()`.
- `core`: `BatchReportScope` (per-batch scope collecting elapsed time, redefined classes, Mixin deltas
  and InitFix stats), `BytecodeSources` (JDK-only registration port for weaving-generated class bytes,
  consumed by `HierarchyTreeOracle.readClassBytes`), `BatchWatchdog`, `StartupGate`.

  field holder, `@Unique private` access, 1→2 same-shape renumbering, field-initializer constructor
  visibility, control stages) plus its own evidence files.

  hotbar model screenshot, real right-click chat assertion); the Toast client entry is intentionally
  removed there. Its end-to-end `runClientGameTest` evidence is carried over from the 1.21.4 template
  round and was **not** re-run after the move (no display session), so it is not counted as new
  verification here.
- `minecraft-fabric-template`: client `HotSwapToast` / `HotSwapToastBridge` / `HotSwapToastModel`
  (`com.example.client`) and `HotSwapToastModelTest` for the model formatting rules (unknown values,
  `delta-known=false`, three-line cap).
- `verifyReleaseCoordinates` (`./gradlew publishToMavenLocal verifyReleaseCoordinates`): asserts that

  `com.github.I-hope1.Remold:*:v<ver>`) under `~/.m2/repository`, so a missing/mismatched publication
  fails the release instead of silently dangling in the templates.

## Known limits / manual acceptance

- **NeoForge 26.x / FML 10+ is not supported and not verified.** That generation removed ModLauncher
  (`cpw.mods:*` is absent from its library list; entry point `net.neoforged.fml.startup.Client`, FML
  loader 11.x). The cross-ClassLoader bridge is written against ModLauncher semantics; do not
  extrapolate the 21.1 evidence.
- **NeoForge production installer launch path is not verified.** The E2E runs a dev runtime
  (ModDevGradle directory classpath). Module ownership can differ in a production launch, so the JPMS
  `--add-opens` requirement must be re-tested there; the agent prints a precise diagnostic instead of
  attempting runtime unsealing.
- **Real client GUI acceptance is still manual.** Container probes cover dedicated servers (Fabric
  KnotServer, Forge `runServer`); the anonymous-class closed loop has not been re-run on a real client
  (IDE + KnotClient), and `docs/acceptance/01-manual-checklist.md` (template scenarios 1–8) still has
  empty result columns for the user to fill in. The Toast card has only been exercised through
  `HotSwapToastModelTest` and entrypoint/listener registration — actual rendering is not verified in
  this environment (no display session).
- **Anonymous-class structural changes still require a restart.** Adding/removing fields or methods on a
  Mixin-generated anonymous class is rejected with a directed diagnostic (member names listed) and never
  bypasses the layout gate. Undecidable alignments are refused rather than guessed: same-shape edits
  whose bodies differ only in literals and whose old class still has live instances are left orphaned,
  with a diagnostic naming the holder fields and the `@RemoldReinit` escape hatch, and
  layout-incompatible candidates are skipped with the same warning — the S5 reading of the probe carries
  one such `[ANON_ALIGN]` refusal for the Mixin host's own anonymous classes, and that edit still takes
  effect for instances created after the change. `ForgeMixinHotSwap` is not wired into this inner-class
  loop, so the anonymous-class hot-swap is Fabric-only for now.
- **plugin and core must be released together.** The suppressor SPI no longer hard-links a core type,
  but a `MixinConfigContext` constructor-signature mismatch still throws `NoSuchMethodError`; it is
  caught per plugin in `RemoldAgent.notifyAssetChanges` and logged as an error, not swallowed. Version
  skew is diagnosable, not supported.
- **`BytecodeSources` has no memory bound.** Its key set does not grow across reloads (the generated
  unique names are stable), but there is no eviction; re-feeding happens before the schema re-check, so
  "the bytes were readable" does not mean "the change took effect".
- **External IDE/JDWP redefine and the `redefineDynamic` single-class channel still run single-phase.**
  The read-through window described in Highlights remains open there: the JVM commits the full new
  bytecode first and Remold can only patch afterwards. Fields rejected by the safety gates are not
  compensated by two-phase either (restart semantics), and before stage B completes a new constructor
  can still read this class's new **static** fields or another class's not-yet-patched fields.
- **Two-phase costs two redefines when it triggers** (a double JIT deoptimization of compiled code);
  pure method-body edits stay single-phase. The `redefineDynamic` single-class entry also has no
  watchdog.
- **`plugin-fabric`'s readiness probe is fail-open and unverified on a real host.** The accessor names
  (`getTicks` / `getTickCount`, `world` / `level`) could not be checked against real sources; when
  probing fails it returns `true` (treated as ready) and logs one info line. `plugin-forge` does not
  implement `isHostReady()` yet.
- **The evidence harness itself has recorded false-PASS / false-kill modes** (exit code 127 recorded as
  a kill, cmd banner-only output recorded as PASS, Gradle `UP-TO-DATE` duplicate stdout hashes treated
  as new evidence). Every PASS / kill figure in this document presumes human review of the raw log;
  tool-side fixes are tracked in `docs/status.md` §0.10.
