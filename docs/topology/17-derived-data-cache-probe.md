# 派生数据缓存实测：粒度、预算与等价性

> **文档类型**：实测记录（只写读数与测量方法；机制状态、验收证据与残余风险以 [`docs/status.md`](../status.md) 为准）

本文件记录 **PR2 派生数据缓存**的量化依据：为什么把缓存粒度定在"单份 blob 的纯派生"、
为什么对齐侧只缓存消费者数据流、条目预算与字节预算各自承担什么，以及这些选择对应的等价性与
变异检查读数。规格与契约见 [`16-bytecode-changeset-vcs.md`](16-bytecode-changeset-vcs.md) §3.7。

## 1. 测量口径

- **同轮次、同语料、单跑**：所有对照都在同一个 JVM 内完成，开/关两档**逐轮交替**测量，
  避免"先测完一档再测另一档"把 JIT 暖机算到缓存头上。已经在并行跑其它任务的机器上不取数。
- **统计量**：一律报 min / median / max。结论须同时对 min 与 median 成立；只对 median 成立时标注"口径敏感"。
- **语料**：仓库自身的编译产物（`<模块>/build/classes`）。对齐侧取"含 lambda 标记的类"（`hasPotentialLambdas`，
  与生产判定同源）；读者侧取整个工程类语料。
- **环境**：JDK 25.0.4.1（Microsoft build），Linux x86_64，堆 1 GiB。
- **探针**：
  - `./gradlew :tests:derivedDataBench`（`tests/src/DerivedDataBench.java`，纯测量 + 一条方向性等价断言）；
  - `./gradlew :tests:readerScanProbe`（`tests/src/ReaderScanProbe.java` §F，带等价断言，计入探针 PASS/FAIL）；
  - `./gradlew :tests:test --tests DerivedDataEquivalenceTest`（门禁用例）。

原始日志：`build/agent-env/logs/pr2-derivedDataBench-final.log`（本机绝对路径，未入库）。

## 2. 对齐侧：现状成本与热点

**每个 lambda 类的 `align()` 成本**（self-align，缓存关）：

| 指标 | 读数 |
|:--|:--|
| 语料 | 229 类，3.70 MiB，平均 16.5 KiB |
| min / median / max | 0.05 ms / **2.02 ms** / 763.76 ms |
| p90 / p99 | 14.15 ms / 229.83 ms |
| 整语料一轮合计 | 2420.3 ms |

投影（median × 每批改动类数）：k=1 → 2.02 ms，k=5 → 10.11 ms，k=20 → 40.44 ms。
注意 max 与 median 差三个数量级：耗时集中在少数超大类（lambda 数多的类），
所以"整语料一轮"的读数被这类类主导，不能用 median 替代。

**热点消融**（既有设计级变异开关 `ACTIVE_MUTATION="4"` 让 `findConsumers` 恒返回空映射）：

| 档位 | min | median | max |
|:--|:--|:--|:--|
| 正常 | 1922.9 ms | 1923.4 ms | 2008.6 ms |
| 关闭消费者数据流 | 114.0 ms | 147.8 ms | 192.2 ms |
| 差值 | — | **1775.7 ms（92%）** | — |

结论（已观测）：ASM `Analyzer` 的消费者数据流是 `align()` 的绝对热点，其余部分（解析、指纹、
骨架/体哈希、匹配循环）合计约占 8%。该消融同时改变了配对结果（少消费者证据 → 配对变少），
所以 92% 是"消费者数据流"的**量级上界**，不是纯耗时项。

据此否决两个候选粒度（以及本切片**未**纳入的候选）：

- 缓存"整类所有方法的消费者结果"（急切派生）：未命中时把类里所有方法都分析一遍，而扫描只走得到
  一部分；在"旧侧命中 + 新侧未命中"的真实批次形态下，过度派生把收益吃掉了（实测 warm ratio 仅 1.09×）。
- 缓存 `align()` 整包结果：`inventedOldNames`、外部匿名类字节、策略开关与 `LAST_RESULT` 发布副作用
  都是输入，两端哈希做键会静默错配（规格 §3.7 已禁止）。
- 缓存形参名 / 骨架哈希 / 体哈希原料：它们不构成独立的重量级派生，而是随同一遍解析顺带产出
  （形参名直接在 `visitMethod` 的回放里收集，不额外读一遍字节）；在"消费者数据流之外仅剩 8%"
  的读数下，为它们引入额外维度（含 `anonHashes` 这类由 resolver 决定的输入）不划算。
- 缓存 `InitFix.NestView` / `HierarchyTreeOracle` 的字节解析：**本切片没有取到该侧读数**，
  因此不做无读数的实现；是否值得缓存留给下一次量化（缺口已在 `docs/status.md` §1.2 登记）。

## 3. 对齐侧：缓存开/关

**开放环（每轮都对整个 lambda 语料 self-align，全部命中）**——这是收益的**上界**：

| 档位 | min | median | max |
|:--|:--|:--|:--|
| 缓存关 | 1985.0 ms | 1990.0 ms | 2004.4 ms |
| 缓存开（冷启动第一轮） | — | 1234.1 ms | — |
| 缓存开（稳态） | 148.7 ms | **166.6 ms** | — |
| 稳态收益 | — | **11.95×** | — |

缓存在稳态下占用：4654 条目 / 2554 KiB。

**跨轮稳态（真实批次形态：旧侧是上一轮的新侧 → 命中；新侧是全新字节 → 未命中）**：
版本链由"同一套 lambda + 一条不同名字的空方法"生成，每轮跑 `align(v[r-1], v[r])`。

| 每批类数 | 缓存关（min / median / max） | 缓存开稳态（min / median / max） | 收益 |
|:--|:--|:--|:--|
| k=8 | 106.50 / 113.30 / 118.34 ms | 64.60 / **66.60** / 83.46 ms | **1.70×** |
| k=229（整语料当一批） | 1966.65 / 2021.01 / 2025.64 ms | 1091.14 / **1111.33** / 1112.08 ms | **1.82×** |

k=8 是本仓库形态下的典型批次规模；两个档位都同时对 min 与 median 成立。

## 4. 读者侧：类型世界与常量池引用

读者扫描每轮对**整个工程类语料**重建类型世界（`universe()`），并在判定阶段对每个类重扫常量池（`refs()`）。
接线形态是"改动前世界 + 改动后世界"两份，同一份未改动的类在两份世界里出现两次。

`ReaderScanProbe` §F（1073 类，5.88 MiB，条目预算 16384、字节预算 8 MiB）：

| 档位 | min | median | max |
|:--|:--|:--|:--|
| 缓存关 | 41.4 ms | 42.5 ms | 54.8 ms |
| 缓存开（稳态） | 17.5 ms | **17.7 ms** | 17.7 ms |
| 收益 | 2.37× | **2.40×** | — |

缓存在稳态下占用：2146 条目 / 3825 KiB（= 每类两条：`readerTypeInfo` + `readerRefs`）。
`DerivedDataBench` §6 在同一语料上给出同向读数（关 51.67 / 83.38 / 87.99 ms，开稳态
21.85 / 22.75 / 22.75 ms，median 收益 3.67×，min 收益 2.36×）。**口径敏感**：收益量级随当轮 JIT/GC
状态在 2.4×～3.7× 之间浮动，方向稳定但幅度不可当成常数。

等价断言（探针内，计入 PASS/FAIL）：缓存开/关的类型世界与引用集合逐项相等（1073 类全等）。

## 5. 预算边界：条目预算必须覆盖一轮工作集

同一份代码、不同预算下的命中行为（读者侧 1073 类 → 2146 条目）：

| 条目预算 | 命中数 | 稳态收益 |
|:--|:--|:--|
| 512（旧默认） | **0** | **0.88×（只剩开销）** |
| 4096 | 2142（第二轮起每轮全中） | 2.6×～3.2× |
| 16384 | 每轮全中 | 2.4×～3.7× |

原因：LRU 在"每轮把同一工作集过一遍"的访问模式下，预算小于工作集时会把上一轮的条目全部冲掉，
命中率退化为 0。同理，对齐侧把整语料（229 类 → 9537 条目）当一批时，4096 预算下命中数同样为 0
（读数 0.96×，即纯开销）；把预算抬到 16384 后恢复 1.82×。

因此默认值调整为：**条目上限 16384，字节上限 8 MiB 不变**。语义上字节预算承担内存上限
（实测每条约 0.5～1.8 KiB，8 MiB 对应约 4500～16000 条），条目上限只作"小值刷屏"的兜底；
需要更紧的内存时调小字节预算即可。两个预算都可用系统属性覆盖，见规格 §3.7。

## 6. 等价性与判定力

门禁 `DerivedDataEquivalenceTest`（5 用例）：

| 用例 | 断言 |
|:--|:--|
| `cacheOnOffProduceIdenticalBytesAndResults` | 三轮版本链下，开/关的产物**逐字节相等** + `AlignmentResult` 全字段相等；开档命中数 > 0、关档命中数与条目数为 0 |
| `reverseGroupOrderKeepsCacheEquivalence` | `TEST_REVERSE_GROUP_ORDER=true` 时开/关仍相等且仍有命中（换序不引入缓存相关的顺序依赖） |
| `consumerCacheIsKeyedPerMethodAndBlob` | 按 `(blob, 方法)` 逐一查条目：每个根方法都有自己的条目、标记表不超过指令流长度、至少一条非空（证明真的走了数据流）、未知 blob 键不解析 |
| `disabledSwitchNeitherPopulatesNorChangesOutput` | 关闭开关既不查也不写缓存，产物不变 |
| `readerFactsCacheIsEquivalent` | 读者侧开/关的类型世界与引用集合相等；pre/post 两世界共用条目（命中数 = 类数）；单轮内不发生淘汰 |

**变异检查**（把键维度故意改坏，对应用例必须变红；每次改完按 md5 校验还原）：

| 变异 | 结果 |
|:--|:--|
| 对齐侧缓存键去掉**方法**维度（同类所有方法共用一张标记表） | `consumerCacheIsKeyedPerMethodAndBlob` FAILED（击杀） |
| 对齐侧缓存键去掉 **blob** 维度（改用常量键） | `consumerCacheIsKeyedPerMethodAndBlob` FAILED（击杀） |
| 读者侧 `refs` 缓存键去掉 **blob** 维度（改用常量键） | `readerFactsCacheIsEquivalent` FAILED（击杀） |

**一个必须记住的教训**（本文件的实测发现）：最初只写了"开/关产物逐字节相等"这一条端到端断言，
上述"去掉方法维度"的变异**存活**——该语料上消费者证据恰好没有改变产物，端到端断言因此假绿。
补上"按方法查条目"的形状断言后才击杀。端到端等价只能证明"用到的派生是对的"，
证明不了"键的维度是够的"。
